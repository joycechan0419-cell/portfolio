A C-END · PRODUCT REDESIGN
把爱奇艺游戏直播间，从「开播工具」做成「用户停留+复访的产品」

在爱奇艺游戏直播业务，主导直播间从工具型到产品化的整体改版——订阅 / 互动 / 礼物 / 留存 4 大核心模块重塑，把直播间从"开播场所"做成"用户停留+复访的产品"。配套支撑周期性活动（军团争霸赛 / 狂欢派对）的运营设计，跑出 流水 70% / 600% 的双周期成绩。

01
背景
爱奇艺游戏直播业务覆盖 iOS/Android 双端，服务千万级活跃用户。早期直播间定位为"主播开播工具"——交互单一、订阅转化低、礼物链路长、用户停留短。运营反馈"直播间只是开播的地方，留不住人"；周期性活动（军团争霸赛 / 狂欢派对）是增长杠杆，但直播间本身的产品力不够承接活动流量。
02
约束
双端体验必须一致（iOS/Android）；不能中断现有开播链路（数千主播同时在线）；改版需在 6 个月内分模块上线；活跃 / 流水 / 停留时长必须可量化；不能影响周期性活动的节奏。
03
探索方案
A 只做视觉改版（界面升级） 被否决：问题不在视觉，在产品结构
B 全量推倒重做 被否决：千级主播在线，全量重做风险太大
C 分模块渐进式改版（订阅/互动/礼物/留存 4 大模块分批灰度上线） 采纳：每个模块可独立验证
04
决策理由
C 把"改版"拆成 4 个产品模块，每个模块都能独立验证对核心指标的影响。直播间产品化 = 让每个模块的设计决策都被数据验证（订阅率、礼物点击率、停留时长、复访率），而不是一次性押注。
05
执行
订阅模块：从"开播提醒"升级为"主播关系沉淀"（订阅卡 / 关注动线 / 订阅福利）；互动模块：弹幕/投票/连麦的体验重塑，强化"参与感"而非"围观感"；礼物模块：从长链路切到"礼物面板+动效反馈"，简化送礼路径+强化礼物的"在场感"反馈；留存模块：直播间底部"主播相关推荐"+直播结束后的"回放/战报"卡片，把单次停留变成多次回访；配套支撑周期性活动：直播间入口嵌入活动 banner，活动期间直播间专属玩法。
06
结果
直播间用户停留时长显著提升；订阅转化率 + 礼物点击率均明显增长；配套支撑的周期性活动（「军团争霸赛」流水 +70%、「狂欢派对」二期流水 +600%）跑出双周期成绩；改版周期 6 个月分 4 个模块灰度上线，单模块可独立验证。
07
反思
直播产品改版的核心不是"加功能"，而是"重新定义直播间的角色"——从"开播场所"变成"用户停留+复访的产品"。早期低估了"主播侧动线"的复杂性，订阅/礼物链路需要主播配合改，沟通成本远超预期；后期成立"主播运营+设计+研发"三方小组才解决。配套活动运营的数据驱动方法（模板×数据）同样适用。
08
可迁移方法
直播 / 增长产品的改版，等于把核心体验拆成可独立验证的产品模块——每个模块都被数据验证，整体改版风险被分摊。

B COMPLEX B-END · IoT
把废宝通过磅系统，从「30+ 分钟」做到「8 分钟」

在德润环保，主导废宝通自助过磅系统 & 纸品交易平台的产品体验设计。打通现场移动端操作与管理端数据可视化——把"称重、交易、供应链"这些重业务流程，做成 1 个产品而不是 N 张 Excel。过磅时间 30+ 分钟 → 8 分钟，错单率 5% → 0.5% 以下。

01
背景
德润环保做再生资源回收，旗下"废宝通"覆盖废纸 / 废金属的自助过磅、交易撮合、供应链结算。早期每辆车过磅要 30+ 分钟（人工录磅单、纸质签字、财务复核、Excel 汇总），业务方抱怨"赚的钱都填在 Excel 里"。现场端用 PDA 拍数字，管理端靠 Excel 汇总——两端数据完全不通，错单率高。
02
约束
现场环境恶劣——户外、强光、雨雪、戴手套触屏、网络弱；过磅流程不能中断（车辆排队有成本）；管理端需要 ERP / 财务 / 供应链 3 套系统的数据汇总；产品要在 6 个月内同时支持现场端和管理端上线。
03
探索方案
A 沿用通用 SaaS 后台模板 被否决：现场操作（手套+强光+弱网）完全不适合桌面级 UI
B 完全照搬 Excel 流程做数字化 被否决：换汤不换药，没有从根上做产品化
C 现场端大按钮+强反馈 + 管理端数据驾驶舱 + 两端实时同步 采纳：两端用不同的设计语言
04
决策理由
C 方案的核心是"两端用不同的设计语言"——现场端要"怎么快怎么来"（单手可操作、按钮 ≥ 56px、关键步骤不超过 3 步），管理端要"怎么全怎么来"（数据可视、决策辅助、跨表查询）；两端通过后端实时同步桥接，而不是靠人搬运数据。
05
执行
现场端 7 步流程拆成"3+2+2"分段：身份识别 → 货品识别 → 重量确认 → 结算 → 离场；每个分段独立页面，单手可达；管理端数据驾驶舱：实时过磅流水 / 异常单据预警 / 客户交易排行 / 库存周转；关键创新：现场端扫码自动调出历史车辆与货品档案，过磅误差自动比对上次记录。
06
结果
单车过磅时间 30+ 分钟 → 8 分钟（−73%）；错单率从约 5% → 0.5% 以下；现场操作工人培训时间 1 天 → 半天；管理端数据驾驶舱覆盖 ERP / 财务 / 供应链 3 套系统的实时数据。
07
反思
重业务流程的产品化，最大对手不是设计水平，而是"业务方愿不愿意改变习惯"——所以新产品的第一步不是炫技，而是用"省 20 分钟"这种立刻可见的收益把一线工人和管理层拉上船，再谈"流程优化"才有人听。低估了"业务浸泡"的时间，前期花了 2 个月完全在客户现场画流程图。
08
可迁移方法
重业务流程产品化，等于「两端分离的设计语言」+「立刻可见的收益」驱动业务方接受新流程。

C B2B · 跨客户 LEAD
让 10 家头部制造企业共享一套配置化 PM

在上海芯港信息，主导基于统一底座做出可配置的业务模板层。客户名单覆盖中车 / 南玻 / 金隅等 10 家头部制造企业——17 个月覆盖，新客户接入从 6 周压到 2 周（−67%）。

01
背景
上海芯港做企业级 PM 系统，客户名单覆盖 10 家头部制造企业（中车 / 南玻 / 帝晶光电 / 国显 / 金隅 / 美克美家 / 星源-采埃孚 / 沈铁科研 / 冀东水泥）。每家诉求看似相似，但关键字段各不相同——单系统服务多客户的典型难题。
02
约束
预算紧、上线快（单个客户预算远低于大客户项目）；客户切换系统的成本是真实的，不能做大改；单一团队要服务近 10 家客户。
03
探索方案
A 复制 10 套独立系统 被否决：开发 × 10、维护 × 10，无法负担
B 一套僵化通用，所有客户照表填 被否决：客户切换成本高，且无法差异化
C 统一底座 + 可配置字段模板 + 客户级差异主题 采纳：把客户差异收敛到「配置层」
04
决策理由
C 方案把「客户差异」抽象为可配置项而非硬编码；同时通过 Theme（色 / Logo）满足品牌差异化——让「配置化的复杂度」由用户承担，而不是研发团队。
05
执行
抽象出 12 个核心字段类型 + 客户级 Theme 切换器 + 后台配置界面；沉淀出两份可复用设计资产——后台设计规范（字段 / 组件 / 权限模板 / Theme 切换器）与数据大屏规范（KPI 卡 / 折线 / 柱状 / 地图 / 排行榜 + 颜色编码），作为后续新客户接入的设计参考；同时建立「新客户接入清单」，把接入流程模板化。
06
结果
17 个月内覆盖 10 家头部制造业客户；新客户接入 6 周 → 2 周（−67%）；沉淀出两份可复用设计规范（后台设计规范 + 数据大屏规范）作为后续客户接入的设计参考；客户 NPS 提升。
07
反思
B 端项目的难度不在设计，而在「抽象」——需要先吃透三家客户的需求差异，才能动手设计配置层。前期投入 2 个月完全浸泡客户现场，不是浪费，是必要。
08
可迁移方法
可配置化的本质，是把客户差异收敛到「配置层」而不是「代码层」。

03 / METHODS · 可迁移方法

从 3 个案例里
提炼出的 3 条方法。

METHOD 01

直播产品改版 = 拆模块 × 数据验证

把核心体验拆成可独立验证的产品模块——每个模块都能被数据验证（订阅率 / 礼物点击率 / 停留时长 / 复访率），整体改版风险被分摊。

延伸经验：周期性活动 / 增长项目同样适用此框架——把"做一版活动"升级为"模板化设计 × 数据驱动迭代"，让增长数据回流到设计决策。

适用场景 直播产品改版 / 增长型产品迭代 / 数据驱动设计
方法来源 案例 01 · 爱奇艺游戏直播间改版
METHOD 02

重业务流程 = 两端分离的设计语言

重业务流程产品化，等于「两端分离的设计语言」+「立刻可见的收益」驱动业务方接受新流程——现场端要"怎么快怎么来"，管理端要"怎么全怎么来"，两端通过后端实时同步桥接。

适用场景 重业务流程产品化 / 工业 IoT / 现场+管理两端系统
方法来源 案例 02 · 废宝通工业物联网
METHOD 03

用后台设计规范 × 数据大屏规范收敛客户差异

从 10 个客户的项目里沉淀出两份可复用设计资产——后台设计规范（12 类字段 / 6 类组件 / 4 类权限模板 / 客户级 Theme 切换器）与数据大屏规范（KPI 卡 / 折线 / 柱状 / 地图 / 排行榜 5 类组件 + 颜色编码）。让客户差异收敛到配置层而不是代码层——研发只做一次，配置可重复 10 次。

适用场景 B 端多客户产品 / SaaS 多租户 / 客户级差异 / 后台设计规范沉淀 / 数据大屏规范沉淀
方法来源 案例 03 · 芯港 10 客户配置化 PM

自我评价

我信「设计不是装饰，是决策」——10 年里我接到的最大挑战从来不是「把页面做漂亮」，而是在业务、设计、工程、高层的边界冲突里，把模糊诉求变成可上线、可衡量、可复用的决策。

我的工作节奏：先跑 3 个客户的最小验证再动手；把「复用率 / 上线指标 / NPS 变化」做成可见信号；用「先做盟友再做规范」推进跨业务线协作。
